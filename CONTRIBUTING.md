# Commit Message Conventions

This project uses semantic versioning with automatic version generation
based on commit messages.

## Testing

### Test Structure

Tests use the DevContainer CLI testing framework with the following structure:

```text
test/<feature-name>/
├── devcontainer.json              # Basic test environment
├── test.sh                        # Basic feature tests
├── scenarios.json                 # Scenario definitions
├── <scenario-name>.sh             # Scenario test scripts
└── scenarios/
    └── <scenario-name>/
        └── devcontainer.json      # Scenario container config
```

### Running Tests

```bash
# Test all features
devcontainer features test .

# Test specific feature
devcontainer features test -f postgresql

# Test specific scenario
devcontainer features test -f postgresql --filter with-uv

# Skip autogenerated tests
devcontainer features test --skip-autogenerated .
```

### Test Types

- **Basic Tests** (`test.sh`): Test the feature in isolation
- **Scenario Tests** (`<scenario-name>.sh`): Test feature combinations and
  specific configurations
- **Autogenerated Tests**: CLI-generated tests with default options
- **Duplicate Tests**: Tests that install the same feature twice with different
  options

## Version Management

Feature versions are maintained manually in each
`src/<feature>/devcontainer-feature.json` file (`version: X.Y.Z`).

When you change a feature, bump the version in that file and update README usage
snippets to the matching major tag (`:<major>`) for the same feature.

The local pre-commit hook checks this automatically:

- `version` in `devcontainer-feature.json` must be valid SemVer (`X.Y.Z`)
- Feature references in `src/<feature>/README.md` must use
  `ghcr.io/the78mole/devcontainer-features/<feature>:<major>`

## Automatic Workflow

On push to `main` (or manual dispatch), the `release.yml` workflow runs and:

1. **Detects Changed Features**: Builds a matrix from the features in `src/`
2. **Reads Per-Feature Version**: Uses the version from
   `src/<feature>/devcontainer-feature.json`
3. **Detects Version Changes**: Compares current feature version against the
   previous commit
4. **Creates Feature Tag**: Creates and pushes `<feature>/v<version>` when the
   version changed
5. **Creates Release**: Publishes a GitHub release per changed feature
6. **Publishes Features**: Pushes features to GHCR via devcontainers/action

### Re-running Release Workflow

Tag creation is idempotent. If a tag already exists (for example after a failed
run that already pushed the tag), the workflow logs that the tag exists and
skips creating it again instead of failing.

## Examples

```bash
# Patch: 1.0.0 -> 1.0.1
git commit -m "docs: update installation instructions"

# Minor: 1.0.1 -> 1.1.0
git commit -m "feat: add connection pooling support"

# Major: 1.1.0 -> 2.0.0
git commit -m "feat!: change default PostgreSQL version to 17"
```

## Pattern Details

Semantic-version commit-message patterns are no longer used for release
versioning in CI.
